# 建模架构与边界

## 当前流程

`configs → ScenarioInputs → controllers → AHU/CO₂ models → data/synthetic`

- adapters：负责输入来源。目前只有假设占用日程，没有将真实传感器历史当成受控房间响应。
- models：纯数值函数，不读数据库、不访问设备、不写文件。
- controllers：只返回模拟指令；目前为固定开度和比例反馈，没有 MPC。
- simulation：编排模型、选择情景、保存输出及完整配置。控制周期默认 60 秒，内部最长 5 秒子步长。
- influxdb：独立的数据采集工具，与 Python 模拟核心分离。

## 房间与 AHU 模型

单房间假定充分混合。CO₂ 方程：

`dC/dt = N * G * 10^6 / V + (Qoa + Qinf) / V * (Cout - C)`

C 为 ppm；N 为假设人数；G 为 m³/s/人；V 为 m³；Q 为 m³/s。每个内部子步采用固定流量下的解析解。渗透换气 `Qinf = ACH * V / 3600`。

实际开度通过一阶执行器趋近指令；假设房间总送风恒定，室外空气比例由开度幂函数给出。这里的指数和上下限只是情景参数，不代表真实风阀压差特性。执行器中点流量用于每个子步的 CO₂ 更新。

模拟比较累计新风体积与 CO₂，而非真实能耗或节能率。没有模拟温湿度、盘管、冷冻水系统、室外颗粒物或 CFD。

## 真实数据和情景的关系

- 历史回放可以评估已有运行方式下的状态预测；当前尚未实现回放适配器。
- 改变模拟控制动作后，未来状态由模拟器推进，不能继续播放真实 CO₂ 并宣称它是该动作的结果。
- 未来将真实 IoT 数据用于初始状态与参数辨识；辨识依赖可观测性，不能只凭 CO₂ 同时任意估计人数、换气和排放。

## 未来 BA 数据边界

建议每个点位具备：`timestamp_utc`、`asset_id`、`point_id`、`value`、`unit`、`source`、`quality`。source 区分 measured、assumed、estimated、synthetic；quality 区分有效、过期、缺失。缺失反馈不能当作 0。

保留独立点位：风阀指令/反馈、总送风/室外新风、风机指令/频率、运行状态、送回风温度、冷冻水阀指令/反馈。见参数说明中的截图点位。

适配器负责单位、时间和点位映射；模型仍只接受统一物理量。待有实测历史后标定开度—流量、执行器延迟及房间参数，再评估 MPC。真实写入 BA 应独立实现，当前项目没有任何设备写入接口。

## IFC 的使用

三个文件均为 IFC2X3。当前静态检查未发现 IfcSpace 或房间体积数量项；传感器用 23 个 IfcBuildingElementProxy 表达。MEP 有端口、系统和送回风口类型，但不等于经过核验的真实气流拓扑。

目前只保存原始文件和哈希，尚未提取房间体积、空间边界或传感器坐标。几何提取后需要确认坐标变换和单位（IFC 长度单位为毫米），传感器对象也需匹配真实设备 ID。渲染模型与计算模型独立维护。

## 真实预测模块（2026-10-18 起）

`forecasting/data.py` 从原始 annotated CSV 构造因果五分钟输入及真实观测标签，独立于 synthetic 模拟。`forecasting/tcn.py` 是因果残差 TCN，直接输出全部预测时距；`forecasting/train.py` 负责时间切分、仅训练段标准化、验证早停与最后一次测试。入口为 `scripts/forecast.py`。

完整路线见根目录 PROJECT_PLAN.md；预测网络不接受假阀门值作为真实控制输入，不用于反事实 AHU 决策。
